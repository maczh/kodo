# 2026-11-27 · kodo 插件加固

## 背景
`github.com/maczh/kodo` 是七牛 Kodo 的 MGin 插件（v1.0.0，仅 client.go + config.go）。本轮做全量审核 + panic 加固 + 连接池/重试 + 双分支挂接。

## 落地的关键结论
- **MGin 接口事实**：v1(jh) `MginPlugin{Init([]byte); Close(); Check() error}`；v2 新契约 `plugin.Plugin{Name/Order/Init(ctx) error/Close(ctx) error/Health/Enabled}`，且 v2 仍保留同签名的 v1 legacy 接口。根包保持 v1 签名不变，v2 适配器放独立模块 `mginv2/`（`github.com/maczh/kodo/mginv2`），避免根模块被 gin/gorm 依赖污染。
- **七牛 SDK 可注入 HTTP 客户端**：`storage.NewBucketManagerEx / NewFormUploaderEx / NewResumeUploaderEx` 接受 `*client.Client{Client: *http.Client}`，这是控制连接池的唯一入口。`storage.MakePublicURL/MakePrivateURL` 不转义 key，必须用 `*v2` 版本。
- **Go recover 陷阱（本轮 P0）**：`defer func(){ recoverToError(&err, op) }()` 中 recover 在 helper 内执行，属于间接调用，**永远拿不到 panic**；必须 `defer recoverToError(&err, op)`（helper 本身作为 defer 函数）。QA 与 lead 各自用最小程序复现确认。
- `isNotFound` 禁止用 `strings.Contains(msg,"612")` 兜底：任何含 612 的文案都会被误判，Delete 会静默成功。改为 `storage.ErrNoSuchFile` / `*qiniu.QError{Code:"612"}` / `*client.ErrorInfo{Code:612}` / 文案收窄。
- 七牛是 HTTP 对象存储，**没有长连接/订阅**；「断线重连/重订阅」的对等实现是：连接池复用 + 幂等操作有界重试（Stat/Delete/List/Check/Download）+ Init 可重入热重载。不要发明订阅逻辑。
- 默认关闭 HTTP/2：qiniu v7.27.0 `internal/uplog` 在 h2 下有 httptrace 跨 goroutine 数据竞争，`-race` 必报；用 `TLSNextProto` 置空规避，配置项 `enableHTTP2` 可开。

## 第二轮：panic 面专项（同日，用户要求「继续深度审核一切潜在 panic」）

新增 9 类修复（见 OVERVIEW 缺陷表 #20–#27）：
- **typed-nil**：`var r io.Reader = (*bytes.Reader)(nil)` 时 `r != nil` 但方法解引用 nil 指针；用 `isNilValue`（reflect，仅可 nil 的 kind）在 Upload/Put/Download/uploadSource/readAllBounded/内部适配器全路径拦截。
- **上传 body 跨协程 panic（本轮最重要的发现）**：请求 body 由 `net/http` 的 writeLoop 协程读取，分片上传还经 `storage.uploadByWorkers` 的 worker 池；业务 Reader/ReaderAt 的 panic 发生在那些协程，方法入口的 `defer recover` **完全无效**，会终止进程。新增 `safeReader`/`safeReaderAt` 包装所有交给 SDK 的读取入口，把 panic 与非法读取计数转 error。
- **日志库本身会 panic**：`gologger` 用 `runtime.Caller(3)`+`FuncForPC`+`parts[pl-2][0]`，栈退化/函数名无包路径时 nil 解引用或越界；recover 路径里再 panic 会直接退出进程。新增 `logging.go` 的 `logInfo/logWarn/logError`（内部 `safeLog` 吞 panic），全部日志改走它。
- `panicText`：panic 值自身 String()/Error() 会 panic 时二次兜底。
- `IsNotFound`/`isRetryable`：typed-nil + 顶层 recover（退化为 false）；`wrapOp` 对 typed-nil 返回 nil；`statusError` nil 接收者保护。
- `MultiError.Error()` 跳过 nil 项（Errors 是对外暴露切片）。
- 整数溢出：`readAllBounded` limit+1；秒级配置 × time.Second（`MaxConfigSeconds`=MaxInt32）；`retryMax` 上限 `MaxRetryCount`=10。
- 其它：`writeAtBuf/writeAtWriter/limitedReader` nil 接收者、WriteAt 负计数钳制、`resp.Body` 判空、`UploadFile` 先校验桶再开文件、导出的 `ParseConfig` 加 recover。

验证：10 个 `_test.go`、110 个 Test 函数、205 个用例；`go test`/`-race`/`go vet`/`gofmt` 全绿；三嵌套模块 build 绿。

## 第三轮：Download 超大对象 OOM（同日，用户要求专项修复）

根因：Go 的 OOM 是 runtime throw，`recover` 兜不住，必须事前拦截。原实现 `DownloadBytes` 直接用流式上限（8GiB）做内存缓冲，且 `writeAtBuf` 2 倍扩容，「旧+新」峰值可达最终大小的 3 倍。

改动：
- 上限分层：`HardMaxDownloadSize`(8GiB) 只给 `Download`/`DownloadFile`；新增 `DefaultMaxDownloadBytes`(64MiB)/`HardMaxDownloadBytes`(1GiB) 与 `DefaultMaxDownloadManyBytes`(256MiB)/`HardMaxDownloadManyBytes`(2GiB)，配置项 `maxDownloadBytes`/`maxDownloadManyBytes`，`normalize()` 钳制。
- `writeAtBuf`：新增 `PresizeDownload(contentLength)` 精确一次性分配；扩容改 1.5 倍 + 64KiB 最小步进；容量上限改用内存硬上限。
- `downloadOnce`：Content-Length 预检后调用 `PresizeDownload`，读 body 前就拒绝超限（谎报长度也不会先分配）。
- `byteBudget`：`DownloadMany` 全批共享总量预算，扩容前 charge；失败 key 按实际 cap 精确 `release`（去掉 release 测试立即失败，已实测）。
- 新 API：`DownloadFile`（流式落盘，不受内存上限）、`DownloadBytesLimit`（单次可上调，钳到 1GiB）。
- 超限错误统一 `sizeLimitError`，给出 Download/DownloadFile/maxDownloadBytes 三条逃生路径。

测试：`memory_download_test.go` 14 个用例（默认值钳制、预检拒绝、cap==len 精确预分配、chunked 扩容不越界、单次上限升降、DownloadFile 绕过内存上限、批量预算 4×600B/1024B 只成功 1 个、失败归还预算、byteBudget 并发精确性、谎报 Content-Length）。
全量：11 个测试文件 / 124 Test / 219 用例，`go test`、`-race`、`-shuffle`、`go vet`、`gofmt`、三嵌套模块 build 全绿。

## 第四轮：ListAll 全量驻留内存（同日，延续 OOM 专项）

根因：ListAll 无任何条数上限，全量结果驻留内存，append 扩容期间还会翻倍；且没有流式遍历入口。

改动：
- 新增 `maxListObjects`（Default 10 万 / Hard 100 万）、`(*Config).listObjectLimit()`、哨兵 `ErrListTooLarge`/`ErrNilCallback`。
- 分页循环收敛为唯一实现 `listPages(ctx, op, prefix, maxObjects, fetch, fn)`：ctx 每轮检查、marker 不推进即退出、超限立即 ErrListTooLarge（不静默截断、不返回部分结果）、取数失败立即返回。
- `(*Bucket).fetchPage` 封装 SDK ListFiles + 幂等重试；`ListAll` 委托 `ListAllLimit`（maxObjects<=0 用配置值，钳到硬上限）。
- 新 API：`ListAllLimit`、`ListEach`（逐条回调）、`ListEachPage`（按页回调）；流式接口不限条数，内存只与单页 1000 条相关。
- `pageFetcher` 函数类型使分页循环可脱离网络单测。

测试：`list_paging_test.go` 10 个用例（多页顺序与 marker 推进、超限报错且不再翻页、恰好等于上限成功、流式 3000 条、marker 不推进不死循环、ctx 取消即停、回调错误原样返回、取数错误、nil fetch/fn、nil 桶、配置钳制）。
实证护栏有效：临时把上限判断改为 false 后 TestListPagesEnforcesMaxObjects 立即失败。

全量：12 个测试文件 / 134 Test / 229 用例，go test、-race、-shuffle、vet、gofmt、三嵌套模块 build 全绿。

## 第五轮：第三轮深度审核（同日，用户「进行第三轮审核」）

这一轮不看 panic 表面，按「配置上限 / 超时分层 / 资源生命周期 / 预算一致性 / 数据正确性」重审，新增 10 条修复（OVERVIEW #33–#42）：

1. `maxUploadMemory` 无硬上限（bufferUnknownSize 可 OOM）→ `HardMaxUploadMemory` 256MiB + normalize 钳制。
2. `chunkSize` 无硬上限（SDK 每并发分片 `make([]byte,0,ChunkSize)`）→ `HardMaxChunkSize` 8MiB，`resolveChunkSize` 统一钳制。
3. 管理类 API 无总超时（v1 SDK 无 ctx，body 卡住即永久挂起，健康检查也挂）→ `newHTTPClients` 拆数据面/管理面，管理面 `manageTimeout`(默认 60s)，**共用同一 Transport**。
4. `DownloadFile` panic 路径不关文件（FD 泄漏）+ 失败留半截文件 → defer 关闭 + 失败 `Truncate(0)`。
5. `DownloadBytes` panic 路径不归还 `byteBudget` → defer 统一归还（panic 先 release 再 re-panic）。
6. `downloadOnce` 的 defer「排空 4KB + Close」panic 会把成功变失败 → `drainAndClose`/`safeCloseBody`。
7. `KeyError.Error()` 对 nil/typed-nil/会 panic 的 Err 不安全 → `errorText`。
8. `ValidateKey` 放过 C1 控制字符 → `unicode.IsControl`。
9. `limitedReader` `remaining+1` 在 limit=MaxInt64 时溢出 → 守卫。
10. mginv2 recover 内 `%v` panic 值可二次 panic → `safePanicText`。

测试：新增 `audit_round3_test.go`（10 用例）。两条护栏做了反向实证：去掉 defer release → 预算用例失败；换回旧 drain defer → body 清理 panic 用例失败。
全量：13 文件 / 144 Test / 239 用例，test、-race、-shuffle、vet、gofmt、三嵌套模块 build 全绿。

## 第六轮：第四轮 panic 审核（同日，用户「继续修复一切可引发panic的bug点」）

视角切换：前几轮解决「panic 打穿边界」，本轮解决「panic 被 recover 之后的二次伤害」，以及「recover 兜不住的假死/静默损坏」。7 条修复：

1. **client.go 抽取 `setResources(cfg,res,state)`**：Init/Close/enabled:false 三处资源替换统一走它，`clientMu` 用 `defer Unlock`。旧写法显式 Unlock，一旦临界区内 panic（被 Init/Close 的 recover 吞掉）就永久锁死 → 后续 Default/Get/Ready 全死锁，比 panic 更难查。
2. **`maxTrustedUploadSize`=5TiB**：`uploadSource` 不再信任 io.Seeker 上报的荒谬长度。SDK 的 `sizedChunkReader.readChunks` 是 `for off < totalSize`，谎报 MaxInt64 会空转数十亿次（CPU 假死）。超限降级 `PutWithoutSize`（结果仍正确）。
3. **`errSeekPositionLost`**：`sizeOfSeeker` 中「已 SeekEnd 但复位失败」必须返回致命错误。旧实现静默降级 → reader 停在末尾 → 上传成功但对象为空（静默数据损坏）。另加 `errNotSeekable`：第一次 SeekCurrent 就失败（管道）属正常，静默降级不刷日志。
4. **`downloadOnce` 错误响应不排空**：`bodyReadToEOF` 标志控制——只有读到 EOF 才 `drainAndClose`，否则 `safeCloseBody`。下载客户端无总超时，服务端「已回头部但 body 卡住」时旧的无条件 drain 会永久阻塞。
5. **下载成功判定收紧为 2xx**：旧 `>=400` 才报错，导致 3xx（无 Location 重定向/304）被当作对象内容写出（静默数据错误）。
6. **parallel.go**：map 写入用 defer 解锁（避免 recover 后 worker 永久阻塞在 Lock、wg.Wait 挂死）；`mapHint` 钳制到 4096（`make(map,len(keys))` 按不可控长度预分配）；`failures` 容量按 64 预估而非 len(keys)。
7. **mginv2.Close 加 recover**（进程退出阶段没有外层兜底）。

测试：新增 `audit_round4_test.go`（15 用例）：荒谬长度/边界值、位置丢失端到端零请求、SeekEnd 失败可降级、不可 seek 静默、真实文件仍精确、错误响应零读取+必 Close+2s 内返回、3xx 拒绝、200 仍排空、mapHint 钳制、setResources 并发不死锁、上传 panic 后 Ready/Names 可用、nil bucket 补齐 4 个方法、控制字符 key。
全量：14 文件 / 159 Test / 254 用例，test、-race、-shuffle、vet、gofmt、三嵌套模块 build+vet 全绿。
